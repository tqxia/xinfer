## What the project does

`xinfer` is a batch-one, BF16 inference proof of concept for Qwen3-0.6B.
Python loads the original Hugging Face model and compiles it ahead of time;
the C++ executable runs model inference and greedy generation without Python.

1. `compiler/prepare.py` applies the non-thinking chat template and converts
   text to token IDs, or saved output IDs back to text.
2. `compiler/model.py` wraps the HF model with an explicit, caller-owned KV
   cache. `TensorCache.update()` writes only the requested positions.
3. `compiler/export.py` uses `torch.export` and AOTInductor to create separate
   `prefill.pt2` and `decode.pt2` packages, including weights and GPU kernels.
4. `runtime/runtime.h` loads both packages, allocates and shares 56 BF16 cache
   tensors, and implements reset, prefill, decode, greedy selection and EOS.
   `runtime/main.cpp` exposes that loop through a token-ID CLI.
5. `compiler/validate*.py` and the native test driver compare HF eager, Python
   AOTI, and C++ results. `compiler/benchmark.py` measures matched workloads.

Prefill accepts 2–512 tokens. Decode accepts one token and also handles a
one-token prompt. The fixed cache holds 1,024 positions and occupies 112 MiB.
Prompt plus requested generation budget must fit the cache. Each package has
its own weight copy. The CLI starts a new process and loads both for each call.

This baseline has no serving scheduler, concurrent batching, paged KV cache,
quantization, native tokenizer, or CUDA Graph replay. The separate Qwen3.5
DeltaNet experiment is outside this setup. `PLAN.md` describes optimization
work; its old host-specific results do not automatically apply to GB10.

## Dependencies and checkpoint

The isolated `.venv` uses Python 3.12, PyTorch **2.13.0+cu130**, Triton **3.7.1**,
and Transformers **4.51.3**. The existing Transformers version is retained to
preserve the cache API used by the adapter. The host supplies CUDA Toolkit 13.0,
GCC 13 and CMake. CMake follows LibTorch's C++ standard (C++20 with this build).

```bash
./scripts/setup-gb10.sh
```

The checkpoint defaults to `work/models/qwen3-0.6b`. Override it with
`XINFER_MODEL_DIR` or the existing `--model-dir` flags. The download helper pins
`Qwen/Qwen3-0.6B` revision `c1899de289a04d12100db370d81485cdf75e47ca` and writes
`model_manifest.json`; all validation runs verify those recorded SHA-256 hashes.
Weights and generated files remain Git-ignored.

NVIDIA cuSPARSELt 0.8.1 publishes an ARM64 wheel whose internal `WHEEL` tag
incorrectly says `manylinux2014_sbsa`. `compiler/fix_cusparselt_metadata.py`
checks the version and AArch64 ELF header, then corrects only that tag and its
`RECORD` checksum. Setup runs this narrow workaround before `pip check`; no
shared-library bytes are changed.

If Hugging Face is unreachable from GB10, download the same revision on a host
with access, using `compiler/download_model.py`, then transfer the complete
directory including its manifest. This setup used a local download, verified
against the official Hub's file metadata, followed by an SSH transfer.

The older `compiler/requirements.txt` and `.lock` describe the original L20
environment. Use `compiler/requirements-gb10.txt` for this branch's GB10 setup;
`compiler/requirements-gb10.lock` records the full tested environment.

## Export, build and validate

```bash
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 PYTHONDONTWRITEBYTECODE=1
export CUDA_HOME=/usr/local/cuda
export PATH="$PWD/.venv/bin:$CUDA_HOME/bin:$PATH"
export TORCHINDUCTOR_COMPILE_THREADS=2
export TORCHINDUCTOR_CACHE_DIR="$PWD/work/inductor-eager"

.venv/bin/python compiler/prepare.py verify
.venv/bin/python compiler/validate.py
.venv/bin/python compiler/export.py decode --eager-numerics --output artifacts/aoti-eager
.venv/bin/python compiler/export.py prefill --eager-numerics --output artifacts/aoti-eager
./scripts/build-gb10.sh
.venv/bin/python compiler/validate_aoti.py --packages artifacts/aoti-eager
.venv/bin/python compiler/validate_cpp.py --packages artifacts/aoti-eager --output artifacts/three-path-eager
.venv/bin/python compiler/tests/smoke_cpp.py --packages artifacts/aoti-eager --output artifacts/native-smoke-eager
```

Reference generation and export intentionally refuse to overwrite existing
artifacts. For another build, choose fresh output directories and pass matching
`--packages`/`--reference` flags to the validators. The packages are specific to
the Torch/CUDA/GPU environment; rebuild them when those dependencies change.

`--eager-numerics` retains eager BF16 rounding behavior using native mean
reductions and disabled floating-point contraction. Numerical validation must
still pass on each new toolchain; the flag alone does not establish parity.

## Optional FlashAttention path

`--attention-backend flash` exports native PyTorch FlashAttention with eight KV
heads and dynamic valid-prefix views inside the compiled model. The runtime retains the same 1,024-token
logical capacity, absolute positions, persistent storage and chunked-prefill
semantics. One padding position per head keeps prefix strides uniform at the
full-cache boundary; the native allocation overhead is 98 KiB (112 KiB in Python), not another KV copy.
The native runtime passes its full cache buffers plus a CPU tensor whose length
is `valid_length + 1`. Only that tensor's shape is read; a view of a persistent
1,025-byte CPU buffer supplies it without copying data or reading a CUDA scalar.
Keeping mutation inputs fixed-size avoids AOTI's size-one specialization of
dynamic mutated inputs. Export also opts into PyTorch 2.13's experimental
`backed_size_oblivious` mode for intermediate prefix views. Native validation and
smoke tests run with `AOTI_RUNTIME_CHECK_INPUTS=1` to verify the entire contract.
The native ATen FlashAttention operator uses lower-right causal alignment and
avoids shape-specializing branches in the public causal-bias dispatcher. This
internal operator is tested with the pinned Torch 2.13 build and its matching
LibTorch. No external flash-attn installation is needed.

```bash
.venv/bin/python compiler/export.py decode --attention-backend flash --output artifacts/aoti-flash
.venv/bin/python compiler/export.py prefill --attention-backend flash --output artifacts/aoti-flash
./scripts/build-gb10.sh
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 .venv/bin/python compiler/validate_cpp.py \
  --packages artifacts/aoti-flash --output artifacts/three-path-flash
PYTHONPATH=compiler .venv/bin/python compiler/tests/flash_attention.py \
  --validation artifacts/three-path-flash --output artifacts/aoti-flash/attention-validation.json
.venv/bin/python compiler/benchmark.py compare \
  --baseline-packages artifacts/aoti --candidate-packages artifacts/aoti-flash \
  --output artifacts/benchmark-gb10-flash
```

This is an **experimental numerical profile**. All 185 tested top-1 predictions,
native/Python AOTI bitwise comparisons, poisoned future slots, cache-write regions,
resets and boundary cases passed. The unchanged 5% full-cache numerical limits
fail on 17/56 tensors (the previous fused baseline fails on 9/56), so
`validate_cpp.py` intentionally exits nonzero after saving the complete report.
Eager FlashAttention reproduces the large backend-dependent cache differences;
isolated attention agrees with an explicit FP32 reference. FP32 model controls
show mixed error changes, not an across-the-board accuracy improvement.
The default export and chat profiles remain unchanged.

The paired benchmark runs four fresh-process rounds in alternating order, with
five measured requests per length/profile/round, two warmups and 64 forced decode
steps. It records package hashes, telemetry, idle checks and prediction agreement.
It does not use CUDA Graph replay. Choose fresh output directories for reruns.
The [measured comparison](benchmarks/gb10-flash-2026-10-24/REPORT.md) records
1.27–1.32× decode throughput and 1.38–1.49× prefill speedups, with the full numerical caveat.

## Run a prompt

```bash
./scripts/chat-gb10.sh 'What is the capital of France? Answer in one short sentence.'
./scripts/chat-gb10.sh '请用一句简短的中文解释什么是机器学习。' 64
```

The helper saves each request under a unique `work/chat.*` directory, tokenizes
offline, runs `build/qwen_aoti`, and decodes the output. Its cold-process timing
includes model loading and is not a steady-state benchmark.

The equivalent native invocation, after tokenization, is:

```bash
./build/qwen_aoti artifacts/aoti-eager work/prompt.ids work/generated.ids --max-new-tokens 64
.venv/bin/python compiler/prepare.py decode --input work/generated.ids
```

### Timing smoke check

One fresh process per execution path, a 25-token prompt, 32 fixed decode steps,
two warmups and five measured requests, with one CPU thread. Both paths use the
same cache layout and fed tokens; all measured prediction IDs agree. CUDA is
synchronized at timing boundaries. Tokenization and loading are outside these
warmed measurements.

| Path | Median prefill | Median decode | Decode rate |
| --- | ---: | ---: | ---: |
| Native AOTI, eager numerics | 15.54 ms | 15.00 ms/token | 66.7 tokens/s |
| Python eager adapter | 23.93 ms | 22.06 ms/token | 45.3 tokens/s |

This was a short-context smoke check with one process round and no idle-boundary
or telemetry protocol. It did not complete the full benchmark in `PLAN.md`

## Completed full benchmark

The [latest full benchmark report](benchmarks/gb10-2026-10-23-rerun/REPORT.md) supersedes the
earlier smoke and low-clock timings. It uses 25/128/512-token prompts, 64 decode
steps, three fresh-process rounds, two warmups and five measured requests per
length per round: 135 measured requests total. All nine workers passed idle
checks before and after.

Eager decode measured 69.3–69.5 tokens/s; AOTI eager numerics measured
91.8–92.0 tokens/s (1.32–1.33x speedup), and fused AOTI measured
97.6–98.0 tokens/s (1.41x speedup). AOTI eager numerics improves
prefill by 1.36–1.38x. Both AOTI profiles match all benchmark predictions.
The same packages retain their prior validation status: eager numerics passes
bitwise parity; fused AOTI fails the full-cache criterion on 9/56 tensors.

Active-sample median SM clocks were 2509–2515 MHz across the profiles. The earlier
[611 MHz run](benchmarks/gb10-2026-10-23/REPORT.md) is retained for comparison; the rerun follows
recovery from the persistent low-clock state. Source, native executable, model,
workload and package hashes match between runs. Automatic clocks were retained.

The report includes variability, memory-accounting limits, first-use/load timing,
numerical status, exact hashes and before/after comparisons. Raw rerun evidence
is under `artifacts/benchmark-gb10-full-rerun-20261023T150003Z/`; compact evidence
is beside the report under `benchmarks/gb10-2026-10-23-rerun/`.

## Fused AOTI profiling

The [profiling report](benchmarks/gb10-profile-2026-10-24/REPORT.md) separates CUDA execution from host waits.
At a representative decode point, linear projections take 7.32 ms/token,
attention plus KV-head expansion 2.14 ms, and GPU-idle gaps 1.04 ms.
The optional CUDA Graph diagnostic improves decode by 8–9% with bitwise
direct/graph parity on tested final logits and full caches. An attention-only
probe demonstrates a native-GQA/valid-prefix opportunity; its speedup is not
an end-to-end model measurement.
