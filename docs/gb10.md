(`ssh tqxia@192.168.1.36`). The branch `dev-gb10-20261030` started from

## Environments and checkpoints

Both environments use Python 3.12, Torch `2.13.0+cu130`, Triton `3.7.1`, and the
GB10 SM121 CUDA toolchain. Their Hugging Face dependencies are isolated:

| Component | Qwen3 | Qwen3.5 |
|---|---|---|
| Python executable | `.venv/bin/python` | `work/gb10-20261030/qwen35-venv/bin/python` |
| Transformers | 4.51.3 | 5.20.2 |
| Tokenizers | 0.21.4 | 0.23.3 |

| Package directory | `artifacts/gb10-20261030/qwen3/packages` | `artifacts/gb10-20261030/qwen35/packages-v2` |

The Qwen3.5 environment links the existing Torch, TorchGen, Functorch, Triton,
NVIDIA/CUDA packages and their distribution metadata from `.venv`; its HF
packages are installed separately. Keep those shared native packages consistent
with the common C++ build. The model requirements files retain the original
Torch 2.7 development pins; the table above describes this GB10 setup.
Qwen3.5 requires Transformers 5.20.2 and an environment without `fla` or
`causal_conv1d`, as enforced by its configuration code.

The existing Qwen3 checkpoint is `Qwen/Qwen3-0.6B` at
`c1899de289a04d12100db370d81485cdf75e47ca`; its `model_manifest.json` records
file sizes and SHA-256 hashes. Qwen3.5 is `Qwen/Qwen3.5-0.8B` at
`2fc06364715b967f1860aea9cf38778875588b17`.

Qwen3.5's raw checkpoint was downloaded on the Mac, verified against the pinned
official Hub metadata, and transferred to `work/models/qwen3.5-0.8b-source`.
GB10 then verified all six files against official sizes/LFS or Git-blob hashes
and the transferred download manifest before extracting 320 text tensors on CPU.
The prepared directory contains `text.safetensors`, config/tokenizer/template
files and `manifest.json`. Its text-weight SHA-256 is
`60be29c75ea732b08a4ee0013d6e89e488f53809b95dd4e1b7713dae113ea45d`.

The scratch extraction and kernel-smoke helpers remain in ignored
`work/gb10-20261030/`. They are setup/diagnostic artifacts, not production modules.
To recheck the transferred source files without changing the prepared model:


## Shared build and shell settings

Use these variables for the remaining commands. Existing exported packages are
retained; select fresh package/output directories when rerunning export or tests.

```bash
Q3_PY=.venv/bin/python
Q35_PY=work/gb10-20261030/qwen35-venv/bin/python
GB_BUILD=work/gb10-20261030/build
Q3_MODEL=work/models/qwen3-0.6b
Q35_MODEL=work/qwen35/0.8b/text
Q3_PACKAGES=artifacts/gb10-20261030/qwen3/packages
Q35_PACKAGES=artifacts/gb10-20261030/qwen35/packages-v2

export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
export TORCHINDUCTOR_COMPILE_THREADS=2
mkdir -p work/gb10-20261030/tmp
export TMPDIR="$PWD/work/gb10-20261030/tmp"
export XINFER_ATTENTION_OPS_LIBRARY="$PWD/$GB_BUILD/libxinfer_attention_ops.so"

"$Q3_PY" -m pip check
"$Q35_PY" -m pip check
"$Q3_PY" -m compiler.qwen3.prepare --model-dir "$Q3_MODEL" verify
```

Both model runtimes share a build linked to `.venv`'s Torch. The Qwen3 native
attention library must be built before Python export. Qwen3.5's GDN Triton
kernels are compiled into its packages and require no separate custom-op
library at inference time.

```bash
GB_TORCH_PREFIX=$("$Q3_PY" -c 'import torch; print(torch.utils.cmake_prefix_path)')
cmake -S . -B "$GB_BUILD" -G Ninja \
  -DCMAKE_PREFIX_PATH="$GB_TORCH_PREFIX" \
  -DCMAKE_MAKE_PROGRAM="$PWD/.venv/bin/ninja" \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc \
  -DTORCH_CUDA_ARCH_LIST=12.1 -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_NLOHMANN_JSON="$PWD/build/_deps/nlohmann_json-src" \
  -DQWEN_BUILD_QWEN35=ON -DQWEN_BUILD_VALIDATION=ON \
  -DQWEN_BUILD_BENCHMARK=ON
cmake --build "$GB_BUILD" --target \
  qwen_aoti qwen_validate qwen_benchmark \
  qwen35_aoti qwen35_validate qwen35_fused qwen35_benchmark -j2
```

The FetchContent override reuses the existing pinned JSON headers on this box.
On a new machine without that cache, omit the override so CMake obtains the
same pinned dependency. Native binaries and exported packages must use matching
Torch/CUDA/ABI and GPU architecture.

## Export on GB10

Serialize GPU compilation and validation. Each entry-point pair must be exported
on GB10 with its corresponding environment and matching compilation settings.
These commands require absent `decode.pt2` / `prefill.pt2` output files.

```bash
export TORCHINDUCTOR_CACHE_DIR="$PWD/work/gb10-20261030/inductor-qwen3"
"$Q3_PY" -m compiler.qwen3.export decode --model-dir "$Q3_MODEL" --output "$Q3_PACKAGES"
"$Q3_PY" -m compiler.qwen3.export prefill --model-dir "$Q3_MODEL" --output "$Q3_PACKAGES"

export TORCHINDUCTOR_CACHE_DIR="$PWD/work/gb10-20261030/inductor-qwen35"
"$Q35_PY" -m compiler.qwen35.export decode --model-dir "$Q35_MODEL" --output "$Q35_PACKAGES"
"$Q35_PY" -m compiler.qwen35.export prefill --model-dir "$Q35_MODEL" --output "$Q35_PACKAGES"
```

Qwen3 uses the canonical fused FlashAttention profile. Qwen3.5 uses its existing
shape-dispatched GDN path and default projection packing: T<=97 takes fused
recurrence and longer prefill takes C64 chunking. The optional Inductor
optimization flag is left off. Both support batch one, prefill T=2..512,
decode T=1 and total context capacity 1,024.

This branch flattens Qwen3.5's internal chunk scratch buffers without changing
their element counts or kernel indexing. It avoids a Torch 2.13 compilation
specialization that narrowed an exported T=2..512 input range to T<=64 when the
tracing example used only one chunk. The tracing example remains T=32 and the
recurrent/chunked threshold remains 97. No padding, alternate attention backend,
or relaxed numerical limits are introduced.

The optional weights-independent smoke helper can check GDN JIT, strict dynamic
export and AOTI at T=1/2/63/64/65/97/98/127/128/129/511/512 before full-model export:

```bash
"$Q35_PY" work/gb10-20261030/smoke_qwen35_kernels_flat.py \
  --output artifacts/gb10-20261030/qwen35-kernel-smoke-new
```

Its scope is backend/functional parity, not HF numerical acceptance.

This branch also stores full-attention K/V in mutable list entries. In this
Torch 2.13 build, export lost the previous tensor-attribute assignments after symbolic
`torch.cond`, leaving attention caches at zero. A CPU probe confirmed that the
cached attribute writer retained a stale Dynamo side-effect table after branch
tracing; list-entry updates use current tracking. The tensor ABI and functional
cache-update semantics are unchanged. See the detailed explanations of the
[workspace shape restriction](experiments/gb10-model-check-2026-10-30.md#qwen35-singleton-chunk-workspace-specialization)
and [lost KV-cache updates](experiments/gb10-model-check-2026-10-30.md#qwen35-lost-kv-cache-updates-after-symbolic-control-flow)
for before/after code, generated graphs, Torch source locations and evidence.
The CPU regression can be run without a model checkpoint or GPU:

```bash
CUDA_VISIBLE_DEVICES='' "$Q35_PY" -m unittest compiler.qwen35.tests.test_text_cache
```

The original `qwen35/packages/` pair predates that fix and is retained only as
failed evidence. Use `qwen35/packages-v2/` as shown above.

## Generate text through the native executables

Choose a fresh manual-run directory. Python only tokenizes and decodes text;
the two native commands perform model inference.

```bash
GB_RUN=work/gb10-20261030/manual-new
mkdir "$GB_RUN"

"$Q3_PY" -m compiler.qwen3.prepare --model-dir "$Q3_MODEL" encode \
  --prompt 'What is 17 + 25? Answer with only the number.' --output "$GB_RUN/qwen3-prompt.ids"
"$GB_BUILD/qwen_aoti" "$Q3_PACKAGES" "$GB_RUN/qwen3-prompt.ids" \
  "$GB_RUN/qwen3-generated.ids" --max-new-tokens 64
"$Q3_PY" -m compiler.qwen3.prepare --model-dir "$Q3_MODEL" decode \
  --input "$GB_RUN/qwen3-generated.ids"

"$Q35_PY" -m compiler.qwen35.prepare --model-dir "$Q35_MODEL" encode \
  --prompt 'What is 17 + 25? Answer with only the number.' --output "$GB_RUN/qwen35-prompt.ids"
"$GB_BUILD/qwen35_aoti" "$Q35_PACKAGES" "$GB_RUN/qwen35-prompt.ids" \
  "$GB_RUN/qwen35-generated.ids" --max-new-tokens 64
"$Q35_PY" -m compiler.qwen35.prepare --model-dir "$Q35_MODEL" decode \
  --input "$GB_RUN/qwen35-generated.ids"
```

## Validate separately from generation

Qwen3 reuses the existing independent HF fixtures in `artifacts/reference`.
Its full validator compares HF, Python AOTI and native results on identical fed
tokens; its smoke suite checks the deployed CLI and package/input rejection.

```bash
AOTI_RUNTIME_CHECK_INPUTS=1 "$Q3_PY" -m compiler.qwen3.tests.validate_cpp \
  --model-dir "$Q3_MODEL" --packages "$Q3_PACKAGES" \
  --reference artifacts/reference --native "$GB_BUILD/qwen_validate" \
  --output artifacts/gb10-20261030/qwen3/three-path-new
"$Q3_PY" -m compiler.qwen3.tests.smoke_cpp \
  --packages "$Q3_PACKAGES" --reference artifacts/reference \
  --native "$GB_BUILD/qwen_aoti" \
  --output artifacts/gb10-20261030/qwen3/native-smoke-new

"$Q35_PY" -m compiler.qwen35.tests.validate_runtime \
  --model-dir "$Q35_MODEL" --packages "$Q35_PACKAGES" \
  --binary "$GB_BUILD/qwen35_validate" --cli "$GB_BUILD/qwen35_aoti" \
  --output artifacts/gb10-20261030/qwen35/runtime-new
"$Q35_PY" -m compiler.qwen35.tests.validate_end_to_end \
  --model-dir "$Q35_MODEL" --packages "$Q35_PACKAGES" \
  --native "$GB_BUILD/qwen35_validate" \
  --output artifacts/gb10-20261030/qwen35/end-to-end-new
```

On this host, a separate VLLM engine currently reserves approximately 103 GiB
of unified memory. Keeping that service running, the ordinary validator can
exhaust memory when its retained CPU snapshots overlap native model loading.
The ignored, self-tested mapped-snapshot runner preserves all checks and limits
while storing snapshots in file-backed tensors:

```bash
AOTI_RUNTIME_CHECK_INPUTS=1 "$Q35_PY" work/gb10-20261030/run_qwen35_mapped_validation.py \
  --module compiler.qwen35.tests.validate_runtime \
  --scratch artifacts/gb10-20261030/qwen35/runtime-manual-mapped \
  --model-dir "$Q35_MODEL" --packages "$Q35_PACKAGES" \
  --binary "$GB_BUILD/qwen35_validate" --cli "$GB_BUILD/qwen35_aoti" \
  --output artifacts/gb10-20261030/qwen35/runtime-manual
AOTI_RUNTIME_CHECK_INPUTS=1 "$Q35_PY" work/gb10-20261030/run_qwen35_mapped_validation.py \
  --module compiler.qwen35.tests.validate_end_to_end \
  --native-receipt artifacts/gb10-20261030/qwen35/end-to-end-v2-native-receipt.json \
  --scratch artifacts/gb10-20261030/qwen35/end-to-end-manual-mapped \
  --model-dir "$Q35_MODEL" --packages "$Q35_PACKAGES" \
  --native "$GB_BUILD/qwen35_validate" \
  --output artifacts/gb10-20261030/qwen35/end-to-end-manual
```

Use fresh scratch and output directories. The larger end-to-end suite also
needs the independently executed native receipt shown above: mmap alone still
left too little memory for its native child. The runner checks the binary,
packages, metadata, validator source, regenerated case-manifest bytes and every
native output checksum before continuing the original comparisons. This receipt
can only be reused with those exact inputs. Its native outputs are retained in
`artifacts/gb10-20261030/qwen35/end-to-end-v2-native-standalone`.

To produce a new receipt for an already generated case manifest, use the
stdlib-only helper in a separate process, with no Python CUDA validator active:

```bash
python3 work/gb10-20261030/run_qwen35_native_handoff.py \
  --binary "$GB_BUILD/qwen35_validate" --packages "$Q35_PACKAGES" \
  --manifest artifacts/gb10-20261030/qwen35/end-to-end-v2/cases.json \
  --output artifacts/gb10-20261030/qwen35/native-manual \
  --receipt artifacts/gb10-20261030/qwen35/native-manual-receipt.json \
  --log work/gb10-20261030/native-manual.log
```

Pass that new receipt to the mapped end-to-end runner. The helpers are retained
host-specific validation aids; they do not change model inference.

Inspect each retained `summary.json`. Qwen3 requires bounded HF logit error and
native/Python exact parity; HF cache/token drift is reported separately.
Qwen3.5 distinguishes `native_runtime_passed` from full HF/FP32 numerical
acceptance. Its end-to-end validator can exit nonzero after saving numerical or
token differences even when native/Python parity holds. Keep these conclusions
separate when deciding whether a model is runnable and numerically accepted.

Generated packages/reports remain in `artifacts/`; environments, build products,
compile caches, transfer metadata and scratch helpers remain in `work/`.
