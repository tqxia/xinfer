# Qwen3.5-0.8B decode: NCU-guided GEMV optimization

The initial experiment below ran on GB10. The appended
[L20 follow-up](#l20-validation-and-comparison-2026-11-13) records validation
and the smaller performance gain on that target.

Experiment dates: 2026-11-12–13, Asia/Shanghai. Started 2026-11-12 22:30:26.
Base revision: f6aba28949ec20375d4130ca3209ca325c950da2 (`codex/xinfer-perf`).
Experiment directory: `work/perf/20261112-qwen35-kernel/` (called `run/` below).
Artifact directory: `artifacts/perf/20261112-qwen35-kernel/`.

## Outcome

On GB10, a decode-only Triton GEMV replacement reduces native decode latency by
18.80–19.06% against the current fused AOTI baseline at the measured contexts.
The final comparison holds all 20 unchanged Inductor kernel configurations
at their baseline choices. The original vocabulary-head implementation is retained.
Both default compilation and controlled re-exports show approximately 19% gains.

| Prompt tokens | Baseline ms/token | Optimized ms/token | Latency reduction |
| ---: | ---: | ---: | ---: |
| 22 | 8.579114 | 6.944116 | 19.0579% |
| 128 | 8.641257 | 7.016905 | 18.7976% |
| 512 | 8.737963 | 7.080512 | 18.9684% |

All nine context/round comparisons improved, by 18.5969–19.4880%.
Median prefill times were 8.336654→8.356499, 18.609818→18.602335 and
49.342640→49.287152 ms respectively. The prefill implementation is identical;
these small timing differences are not claimed as a prefill optimization.
The candidate passes the current numerical policy, with strict native/Python
parity. HF-relative state/token diagnostics remain and increase in some cases;
the implementation is not bitwise equivalent to the previous model.

The implementation was first developed on `codex/gb10-qwen35-gemv-20261113`
from the tested base revision. Its GEMV commit was later rebased onto `main`
independently of the performance-plugin work. The original optimization session
used the isolated `run/source/` worktree; raw profiles, packages and scratch
drivers remain in ignored experiment directories.

## Scope, environment and measurement

- Batch-one BF16 Qwen3.5-0.8B, pinned checkpoint revision
  `2fc06364715b967f1860aea9cf38778875588b17`.
- GB10 SM 12.1, driver 580.159.03; Torch 2.13.0+cu130
  (git cf30153c4c131c8164ee7798e5022d810682e2cb), Triton 3.7.1,
  Transformers 5.20.2, CUDA 13, NSYS 2025.3.2 and NCU 2025.3.1.
- Compiled context capacity 1,024; prefill supports 2–512 tokens/call;
  decode contains one new token. Optional Inductor tuning remains off.
- Existing project paired C++ comparator: three rotated rounds, two warmups,
  five measured requests/round, 32 forced decode steps, lengths 22/128/512.
  This yields 90 measured requests and 2,880 measured decode tokens.
- Primary timing includes argmax and host reads. Accuracy validation and
  profiling are separate from the unprofiled native timing.
- All 12 benchmark idle checks passed. Allocation/reservation peaks match.
  The benchmark's sampled busy clocks were 2,450–2,496 MHz. The independent
  500 ms monitor recorded busy P0 clocks 2,405–2,496 MHz and no 611 MHz sample.
  Sampling is not continuous proof of exclusivity or absence of every transient.

Existing weights/environment were reused. Old November 10 packages lacked
the now-bundled attention dependency, so current native targets and a fresh
baseline were built/exported. A stalled CMake dependency download was replaced
by an independent copy of the retained pinned nlohmann JSON source.
Original builds, caches and packages were preserved.

## Baseline evidence and target selection

The fresh baseline passed 202 CPU tests, native state/generation contracts,
and full HF → adapted eager → Python AOTI → C++ AOTI validation.
A same-bundle A/A comparison showed at most 0.145% pooled-median separation.

Fresh NSYS attribution used the runtime synchronization pattern, request
ordering, scalar prediction-copy counts and native timing crosschecks.
It did not use whole-process totals or an arbitrary time cutoff.

Baseline measured decode has 276 launches/token and 8.189325 ms/token of GPU
kernel duration. The 96 decoder projections consume 5.643761 ms/token (68.92%);
the vocabulary head consumes 2.155282 ms/token (26.32%). Together, projections
account for 95.23% of GPU kernel duration.

Baseline NCU identified 164 registers/thread in decoder cuBLAS GEMVs,
register-limited 25% theoretical occupancy, approximately 21–24% achieved
occupancy, few eligible warps and scoreboard/LG-throttle stalls.
The head uses 72 registers/thread and 17.4 KB dynamic shared memory,
with approximately 41% occupancy and substantial dependency/barrier stalls.
No DRAM counters were present in the collected metric set; this experiment
does not claim measured DRAM saturation.

The brief elimination review found last-token vocabulary projection and valid
cache-prefix attention already implemented. Prefill-only row elimination
does not remove work from this T=1 decode path.

## Implementation

The implementation is split across shared kernels/passes, Qwen3.5 export and tests:

- `compiler/common/kernels/projection_gemv.py`: read-only
  `torch.library.triton_op`/`wrap_triton` implementation with FP32 accumulation,
  an eager launch requesting disabled FP fusion, masked reduction/output tails
  and fresh output storage. See the packaging caveat below.
- `compiler/common/passes/projection_gemv.py`: replaces eligible bias-free,
  frozen BF16 singleton-row projections after packing, preserving parameter
  identities, signatures and output metadata.
- `compiler/qwen35/export.py`: applies the pass to decode and records its
  replacements. All 96 decoder projections are replaced; the tied head is excluded.
- `compiler/common/tests/test_projection_gemv.py`: graph-contract/exclusion tests.
- `compiler/common/tests/test_projection_gemv_cuda.py`: repeatable numerical,
  buffer/stream and Python-AOTI packaging checks, without checkpoint downloads.

The kernel handles a contiguous weight matrix [N,K] and one logical input row.
The selected configuration uses four rows/program for K=1024 and one row/program
for K>=2048, four warps and one stage. The graph pass is restricted to the
five profiled decoder geometries; unknown geometries keep their existing path.

Six packaged specializations cover five geometries. All six X/Weight/Output
pointer signatures are BF16. The extra specialization is the full-attention
output projection at [K,N]=[2048,1024], whose input lacks a 16-byte-divisibility
annotation; it uses more shared memory than the Delta output variant.
This is conservative compiler alignment metadata, not evidence of a misaligned
runtime pointer. No unconditional alignment assumption was added.

The measured four-file snapshot is retained as `run/candidate1-source.patch`
(SHA256 `18bd73210dfff3e5fd381ab48b4d7069c6596dee47d78a487e14388397f35c53`).
Forward and reverse apply checks passed. This branch also retains compact CUDA
regression tests and current usage documentation; those additions do not change
the measured kernel or exporter implementation.

## NCU-guided inner loop

The local baseline used the actual layouts, checkpoint weights and synthetic
activations. The dense kernel has no data-dependent dispatch. Complete-call
CUDA-event timings used alternating order and 64 MiB cache pressure outside
the timing interval. Python dispatch/idle gaps can affect these measurements;
they are not native-model or pure-kernel latency claims.

### Decoder R1: four rows/program, four warps

The hypothesis was that fewer live values/registers would improve latency
hiding. All 40 BF16/FP32 binary-fraction, cancellation, random and real-weight
checks passed against cuBLAS and an independent CPU FP64→FP32 reference.

Matching local NCU for [K,N]=[1024,8224] showed 164→34 registers/thread,
23.56→89.71% achieved occupancy and 99.360→79.232 microseconds of profiled
kernel time. Eligible warps improved only modestly. Local complete-call gains
were mixed: the narrow-output cases improved approximately 14–21%, while
the large packed projections were roughly flat.

Before extensive tuning, a constant-free two-input AOTI package passed
Python bitwise checks and a standalone C++ loader proof with no Python library.

### Decoder R2: one row/program for long reductions

R1's K=3584,N=1024 case had only 256 CTAs and about 42% achieved occupancy.
R2 raised its grid to 1,024 CTAs while retaining four rows for K=1024.
The hypothesis predicted more independent work and lower register pressure;
extra scheduling/reduction overhead was the refuter.

All 40 checks passed again. Matching NCU showed 58→40 registers/thread,
41.90→84.58% occupancy, eligible warps 0.0494→0.0853 and issue activity
4.29→6.46%. Profiled time changed modestly, 34.976→34.176 microseconds.
Paired complete-call gains versus the original were about 23.6% for K=2048
and 16.7% for K=3584. R2 was selected for full-model export and measurement.
Occupancy alone was not used to declare success.

### Vocabulary-head screen: not integrated

The unchanged head remained approximately 31% of GPU kernel time after R2.
Two local configurations passed all eight BF16/FP32 head checks each:

| Head configuration | Baseline microseconds | Candidate microseconds | Local reduction |
| --- | ---: | ---: | ---: |
| 4 rows / 4 warps | 2066.656 | 2023.664 | 2.0803% |
| 16 rows / 8 warps | 2067.728 | 2046.704 | 1.0168% |

R1/R2 achieved approximately 97.6/98.6% occupancy. R2 had more eligible warps
and lower long-scoreboard share, but more barrier share and worse timing.
The best 42.99-microsecond saving would imply only about 0.61–0.62% of
C1 model latency if it translated. That is a hypothesis, not a native result.
The head was deprioritized; its graph pass and production implementation were not changed.

## Controlling unrelated compiler changes

Default R2 compilation changed four unrelated common-kernel launch choices
because generated names lost `unsafe_view` components and missed old tuning
cache entries. Copying the baseline cache did not guarantee isolation.

A guarded four-configuration re-export restored those choices but fresh tuning
changed two other pointwise configurations. Their combined baseline cost was
0.011488 ms/token. All variants were retained rather than selecting favorable data.

The final control pins all 20 unchanged-body Inductor kernels to their actual
baseline configurations. The fixed Delta kernel is checked separately.
The scratch hook guards Torch git/version, private source hash/signature,
normalized kernel name and exact arithmetic AST, and selects only existing
legal configurations. FX graph cache is disabled and compilation synchronous.
This hook is experiment tooling, not part of the proposed production change.

Final artifact checks:

- Prefill graph and all 30 kernel source bodies/CUBINs/instruction bytes/launches match baseline.
- Decode contains 96 custom projection calls and one original tied-head mm.
- All 22 common decode grid/launch configurations match baseline.
- 21/22 common instruction bodies match byte-for-byte.
- Norm 6 retains its arithmetic/rounding chain but uses separate output storage
  instead of an in-place reused buffer. This integration-induced memory-planning
  exception prevents claiming perfect instruction identity outside the 96 GEMVs.
- All six GEMV specializations retain R2 instruction bytes and launch settings;
  attention-library bytes match baseline.
- Official comparison checks accept identical logical identity and all 231
  source-weight mappings; a separate manifest audit also confirms unchanged
  constant mappings. No integrity check was bypassed.

## Full-model correctness and native closure

Final all-common controlled validation passes the current shared_bf16 v1 policy:

- Zero required failures; 19,217/19,217 native/Python bitwise records.
- Required finite, state ownership, KV writes/masking, reset/reuse and storage checks pass.
- Worst direct AOTI/HF logit L2 is 3.269534%, peak-relative 1.731602%, below 5%.
  Baseline values were 3.006781% and 1.461314%.
- Diagnostics: 17,220 total, including 17,207 state, 11 teacher top-token and
  two greedy records; baseline had 16,901 total diagnostics.
- A compiled capital-answer greedy example adds a period. This difference
  remains diagnostic under current policy; it was not hidden or fixed.

Standalone numerical limits remained 1% BF16 and 0.01% FP32, with the existing
FP32 absolute-roundoff allowance. Twelve additional odd-tail/layout GPU checks
passed. Schema/fake checks, input immutability, output ownership and
nondefault-stream eager/Python-AOTI checks passed.

The original 202 CPU checks passed before the experiment; nine focused CPU
checks pass for the measured proposal. Its four-file snapshot passed pinned
Ruff 0.17.3 formatting checks.
Formatting changed only the pass/tests, with identical ASTs; kernel/exporter
file hashes remained unchanged from the measured implementation.

Final native NSYS confirms 276 launches/token, 96 custom projections plus one head,
valid phase/grid attribution, 4.033854 ms/token in decoder projections and
2.005133 ms/token in the unchanged head. GPU kernel sum is 6.445264 ms/token;
profiled wall time is 7.084667 ms/token, separate from unprofiled timing.
Packaged NCU covers all six specialization instances, including the alignment variant.
The unchanged head's different measured duration is not a head-optimization claim.

## Publication regression checks

The publication branch adds reusable tests without changing the measured kernel
or exporter file hashes. Nine focused CPU tests and all four new CUDA test
methods pass on GB10. The CUDA suite covers all five decoder geometries in
BF16/FP32, odd tails, independent CPU FP64-to-FP32 controls, exact binary cases,
input immutability, fresh outputs, offset/singleton layouts, nondefault streams
and constant-free Python AOTI packaging. All five changed Python source files
pass pinned Ruff 0.17.3 formatting checks.

The added packaging fixture exposed a compilation detail: the eager launch
requests `enable_fp_fusion=False`, but captured user-kernel metadata omits that
option and AOTI compiles this fixture with `enable_fp_fusion=True`. The flag
propagation gap is confirmed in the installed Torch/Triton source and cache
metadata. Diagnostic PTX confirms separate FP32 multiply/add for eager and FMA
for AOTI. All six measured packaged GEMV CUBINs also match cache entries with
fusion enabled, so the native timing and packaged NCU evidence already describe
that compiled implementation. For the FP32 K=33,N=7 fixture, eager/AOTI maximum
absolute difference is 1.1920929e-7 and relative-L2 difference is 6.6683e-8.
Both independently pass
the existing FP32 numerical limit, and repeated execution of the same AOTI
package is bitwise identical. BF16 eager/AOTI is bitwise identical in the fixture.

The retained packaging test requires independent numerical controls and AOTI
repeatability for both dtypes, plus eager/AOTI bitwise equality for BF16. It
does not impose cross-compiler FP32 bitwise equality. The graph pass remains
BF16-only; no production arithmetic, numerical threshold or strict full-model
native/Python AOTI acceptance rule was changed for publication. These checks
supplement the full-model validation above.

## Repeating the retained implementation

Select `Q35_PY` and the matching build environment from the
[target environment guide](../../environments/README.md), prepare the pinned
0.8B checkpoint, and build the Qwen3.5 native/attention targets described in
the [model guide](../../compiler/qwen35/README.md). Use fresh output directories.
Export the baseline at the base revision above and the candidate on this branch,
using the same checkpoint, capacity and optional compiler settings:

```bash
MODEL_DIR=work/qwen35/0.8b/text
BUILD=build/qwen35
BASELINE_PACKAGES=artifacts/aoti-gemv-baseline
CANDIDATE_PACKAGES=artifacts/aoti-gemv-candidate

# At the base revision, use --output "$BASELINE_PACKAGES" instead.
"$Q35_PY" -m compiler.qwen35.export --model-dir "$MODEL_DIR" \
  --max-context-length 1024 --output "$CANDIDATE_PACKAGES"
"$Q35_PY" -m tools.validation.validate --model-dir "$MODEL_DIR" \
  --packages "$CANDIDATE_PACKAGES" --native "$BUILD/xinfer_validate" \
  --output artifacts/validation-gemv-candidate
"$Q35_PY" -m tools.benchmark compare --model-dir "$MODEL_DIR" \
  --baseline-packages "$BASELINE_PACKAGES" \
  --candidate-packages "$CANDIDATE_PACKAGES" \
  --native "$BUILD/xinfer_benchmark" --gpu 0 --lengths 22 128 512 \
  --decode-steps 32 --warmup 2 --repeats 5 --rounds 3 \
  --output artifacts/comparison-gemv-candidate
```

These commands exercise the retained default implementation. The final historical
comparison above additionally used the guarded, version-specific scratch hook
to control unrelated Inductor launch choices; that hook is not installed by this
branch. Keep the normal numerical checks and idle/clock checks enabled on reruns.

## L20 validation and comparison, 2026-11-13

The same implementation completed export, full-model validation and C++
execution on L20 SM 8.9. The retained stack uses driver 550.54.15,
Torch 2.13.0+cu126 (the same Torch Git revision as GB10), Triton 3.7.1 and
Transformers 5.20.2. Checkpoint, BF16 batch-one execution, context capacity
1,024 and optional Inductor tuning off match the GB10 experiment.

### Controlled native results

| Prompt tokens | Baseline ms/token | Optimized ms/token | Latency reduction |
| ---: | ---: | ---: | ---: |
| 22 | 2.786598 | 2.740196 | 1.6652% |
| 128 | 2.790042 | 2.754833 | 1.2620% |
| 512 | 2.803692 | 2.784823 | 0.6730% |

The existing paired C++ comparator used four rotated process rounds, two
warmups, five measured requests per workload/arm/round and 32 forced decode
steps: 120 measured requests and 3,840 decode tokens. All 12 context/round
comparisons improved, with reductions of 1.4687–1.9652%, 1.1029–1.6391% and
0.4432–0.9112% respectively. The matching A/A control showed 0.1414–0.2227%
pooled signed drift with the candidate label slower, and at most 0.4824%
absolute per-round drift. The weakest 512-token round overlaps that variation;
A/A is an empirical noise comparison, not a confidence bound or a correction
subtracted from the gains.

All 16 comparison idle checks and 16 final A/A idle checks passed. Sampled busy
SM clocks held at 2,520 MHz. Peak allocated, reserved and sampled device memory
matched baseline for every workload. Prefill medians were 3.939931→3.929692,
8.377520→8.336167 and 20.116258→20.170817 ms; these small differences are not
claimed as a prefill optimization.

An initial default-export comparison showed 0.5892–1.7153% decode reductions,
but independent autotuning also changed seven prefill configurations and three
common decode grids. A guarded scratch re-export restored every common baseline
configuration, using only existing legal choices. All 30 prefill CUBINs then
matched baseline; all 22 common decode launch configurations matched. Of these,
21 retained identical normalized arithmetic and complete Triton metadata.
Norm 6 kept the documented separate residual-output storage change with the same
arithmetic/rounding chain. GDN retained identical CUBIN bytes and launches.
All six GEMV specializations matched the default candidate's binaries and
configurations. The table above reports this controlled comparison; the hook
remains experiment tooling, outside the production exporter.

### Correctness and interpretation

All 38 focused CPU checks, both native state/generation contract executables,
four retained CUDA test methods and eight additional production-shape AOTI
checks passed. The latter cover all five BF16 geometries, an offset K=2048 input
and two FP32 controls against independent CPU FP64→FP32 references, with the
existing component tolerances. All six BF16 eager/AOTI cases were bitwise equal.

Baseline, default candidate and controlled candidate passed full
HF → eager → Python AOTI → C++ validation under shared_bf16 v1:

- Zero required failures; candidate native/Python parity was 19,216/19,216
  exact tensor records, versus baseline 19,217/19,217.
- All 381 teacher/state checkpoints per main stage remained. Candidate capital
  generation removed the baseline's extra period, producing four instead of
  five tokens and explaining the smaller native/HF-replay record counts.
  All three candidate greedy examples matched HF/eager.
- Worst direct AOTI/HF logit relative L2 rose 3.144832→3.554678% and
  peak-relative rose 1.493750→1.700000%, both below the required 5% bounds.
- Diagnostics rose 17,075→17,653: 583 additional state findings, three fewer
  teacher-top1 findings and two fewer greedy findings. Contract checks passed.
  Default and controlled comparison/diagnostic arrays matched exactly; raw
  default-versus-controlled tensor-payload equality was not asserted.

The fixed-token timing inputs and 32 decode steps were identical across arms.
One predicted ID differed in the 22-token workload; longer-workload predictions
matched. This diagnostic difference did not shorten the timed workload or change
the strict native/Python parity requirement.

The smaller gain starts inside GEMV itself. Native NSYS measured decoder
projection GPU time of 1.565934→1.517534 ms/token on L20, a 3.09% reduction,
compared with 5.643761→4.033854 ms/token on GB10, a 28.53% reduction.
Both retain 276 launches/token and the original vocabulary head.
For K=1024,N=8224, L20 NCU showed 168→34 registers/thread and
22.92→80.91% achieved occupancy, but DRAM throughput improved only
751.78→770.40 GB/s. More resident warps therefore delivered only a modest
memory-throughput improvement on this target.

Other costs offset part of L20's roughly 48-microsecond projection saving:
GDN GPU duration rose 0.060995→0.084566 ms/token despite identical code and
launches. Cache/scheduling interaction or profiling effects remain hypotheses.
The GPU-duration sum fell 2.577295→2.559017 ms/token; profiler measurements
remain separate from unprofiled native timings. Matching NCU captures cover all
six packaged GEMV specializations. These captures used the default candidate;
its identical binaries/configurations support kernel analysis without relabeling
the captured counters as controlled-model measurements.

Functional L20 support is established for this matrix, with a modest native
gain. The approximately 19% claim remains specific to GB10. Different CUDA/cuBLAS
stacks and missing GB10 DRAM counters prevent assigning the entire difference
to a single architectural cause. The L20 evidence is retained separately under
`work/l20-gemv-20261113/`, including validation summaries, paired results,
artifact audits and native NSYS/NCU captures. No profiler wrapper or runtime
change was added.
