# Qwen3.5 decode GEMV: design and measured results

This case study explains the decode projection replacement retained in the
compiler. Measurements were made on November 12–13, 2026, starting from revision
`f6aba28949ec20375d4130ca3209ca325c950da2`. They are specific to the tested
0.8B bundles, targets and workloads, not a claim about every subsequent build.
The [original investigation][journal] preserves the complete trial history and
artifact identities. Current commands are in the
[model guide](../../compiler/qwen35/README.md) and
[benchmark guide](../development-tools.md#compare-two-compiled-profiles).

## Scope and implementation

The model was batch-one BF16 Qwen3.5-0.8B at checkpoint
`2fc06364715b967f1860aea9cf38778875588b17`, with capacity 1,024, prefill 2–512
and single-token decode. Packing was already enabled; optional Inductor tuning
was off. Both targets used Torch 2.13.0 (Git `cf30153c4c131c8164ee7798e5022d810682e2cb`),
Triton 3.7.1 and Transformers 5.20.2: cu130 on GB10 SM12.1, cu126 on L20 SM8.9.

Native profiling attributed about 95% of GB10 decode kernel time to projections:
96 decoder GEMVs consumed 68.92%, and the vocabulary head 26.32%. The baseline
had 276 launches/token. Decoder kernels used 164 registers/thread with roughly
21–24% achieved occupancy and dependency stalls. No GB10 DRAM counters were
collected, so this did not establish measured DRAM saturation.

The retained implementation has three parts:

- [`projection_gemv.py`](../../compiler/common/kernels/projection_gemv.py) implements
  a read-only Triton singleton-row projection with FP32 accumulation, masked
  tails and fresh output storage.
- [The graph pass](../../compiler/common/passes/projection_gemv.py) selects frozen,
  bias-free BF16 projections in five profiled decoder geometries after packing.
  It preserves parameters, signatures and output metadata. Unknown geometries
  and the tied vocabulary head keep their existing linear path.
- [Qwen3.5 export](../../compiler/qwen35/export.py) applies it to decode only.
  The measured 0.8B graph replaced 96 projections and retained the original head.

Four rows/program work well for `K=1024`; one row/program for `K>=2048` increases
parallelism for the longer reductions. Both use four warps and one stage.
For `K=3584,N=1024`, changing four rows to one raised the grid from 256 to 1,024
CTAs and measured occupancy from 41.90% to 84.58%. The design was selected using
complete-call timing and native validation, not occupancy alone.

Six packaged specializations cover five geometries. The full-attention output
projection at `[K,N]=[2048,1024]` lacks a 16-byte-divisibility annotation and uses
more shared memory than the Delta variant. This is conservative compiler metadata,
not proof of a misaligned runtime pointer. No unconditional alignment assumption
was added; extensions need a proven producer contract or safe dispatch.

## Controlled native results

| Device | Prompt tokens | Baseline ms/token | GEMV ms/token | Reduction |
| --- | ---: | ---: | ---: | ---: |
| GB10 | 22 | 8.579114 | 6.944116 | 19.0579% |
| GB10 | 128 | 8.641257 | 7.016905 | 18.7976% |
| GB10 | 512 | 8.737963 | 7.080512 | 18.9684% |
| L20 | 22 | 2.786598 | 2.740196 | 1.6652% |
| L20 | 128 | 2.790042 | 2.754833 | 1.2620% |
| L20 | 512 | 2.803692 | 2.784823 | 0.6730% |

The paired comparator used identical fixed-token inputs, 32 forced decode steps,
two warmups and five measured requests per workload/round. GB10 used three
rotated rounds; L20 used four. Timing includes argmax and host reads. All
before/after idle checks passed; sampled busy clocks were healthy. Samples are
not continuous proof of exclusivity. Profiler measurements were separate from
these unprofiled native timings.

All nine GB10 context/round comparisons improved. The A/A control showed at most
0.145% pooled-median separation. All 12 L20 comparisons improved, but the weakest
512-token round overlapped the observed A/A variation (up to 0.4824% per round).
A/A is an empirical noise check, not a confidence bound or a correction to
subtract from the gain. No prefill optimization or memory reduction is claimed;
measured memory peaks matched baseline.

The smaller L20 benefit begins inside GEMV: native decoder-projection GPU time
fell only 3.09%, versus 28.53% on GB10. On L20, one projection's registers fell
168→34 and occupancy rose 22.92→80.91%, but measured DRAM throughput improved
only 751.78→770.40 GB/s. More occupancy did not imply proportional throughput.
Other costs offset part of the saving; GDN timing changed despite identical
code and launches. Cache/scheduling interaction and profiling effects remain
hypotheses, not established causes.

The head stayed unchanged. Local head configurations gave only 1–2% local
improvements, implying roughly 0.6% model headroom at best if translated.
Higher occupancy alone did not solve its cost. No native head-optimization result
is claimed. Runtime and CUDA Graph changes were outside the experiment.

## Controlling compilation effects

A focused graph rewrite changed unrelated Inductor tuning choices because kernel
names changed and missed retained cache entries. Copying the baseline cache did
not guarantee an isolated comparison. Controlled re-exports restored existing
legal baseline choices for all unchanged-body kernels; the guarded scratch hook
was not added to production.

For the final GB10 control, prefill graphs and all 30 prefill kernel bodies,
CUBINs and launch choices matched baseline. All 22 common decode launch choices
matched; 21 common instruction bodies were byte-identical. One normalization
retained its arithmetic/rounding chain but used separate residual output storage.
That exception prevents claiming perfect instruction identity outside GEMV.
The six GEMV specializations retained the candidate's binaries/configurations,
and logical weights/source mappings remained unchanged.

L20 also required a control for unrelated default-export tuning changes. All
30 prefill CUBINs and 22 common decode launch configurations matched its baseline;
GDN retained identical binaries. Default and controlled candidates retained the
same GEMV binaries and validation metrics. This supports attribution without
calling a default-candidate profiler capture a controlled-model measurement.

## Correctness and compilation caveat

The final candidates passed the current `shared_bf16 v1` policy:

| Check | GB10 | L20 |
| --- | ---: | ---: |
| Required failures | 0 | 0 |
| Exact native/Python tensor records | 19,217 | 19,216 |
| Worst direct AOTI/HF logit relative L2 | 3.269534% | 3.554678% |
| Worst direct AOTI/HF peak-relative error | 1.731602% | 1.700000% |
| Diagnostic findings | 17,220 | 17,653 |

Finite outputs, ownership, KV writes/masking, reset/reuse and storage checks
passed. HF state/token diagnostics remained and some increased. On L20 the
candidate removed the baseline's extra period in one greedy example, explaining
one fewer native/replay record; all three candidate greedy examples matched HF.
One fixed-token benchmark prediction differed, but the timed inputs and decode
count remained unchanged. These results are not bitwise baseline equivalence or
proof of equivalent task quality; [validation status](../validation-status.md)
keeps their scope separate from 4B and expanded-context coverage.

A packaging test exposed a Torch/Triton option-propagation gap: eager launch
requested `enable_fp_fusion=False`, but captured user-kernel metadata omitted it,
and AOTI compiled with fusion enabled. All six measured GEMV CUBINs used fusion,
so the native results above already describe that packaged implementation.
For an FP32 `K=33,N=7` fixture, eager/AOTI maximum absolute difference was
1.1920929e-7. Both independently passed the existing numerical limit; repeated
execution of one package was bitwise. BF16 eager/AOTI was bitwise in the fixture.

Retained [CPU](../../compiler/common/tests/test_projection_gemv.py) and
[CUDA/AOTI](../../compiler/common/tests/test_projection_gemv_cuda.py) tests cover
eligibility, actual geometries, tails, offset/singleton layouts, ownership,
nondefault streams and independent CPU FP64→FP32 controls. Limits remain 1% BF16
and 0.01% FP32 with the existing roundoff allowance. Packaging requires independent
controls and repeatability for both dtypes plus eager/AOTI bitwise equality for
BF16, not cross-compiler FP32 bitwise equality. Production rewrite eligibility
remains BF16-only; strict full-model native/Python parity is unchanged.

## Applying the conclusions

Use fresh bundles and the current validation/paired-benchmark commands. To
reproduce this profile, explicitly select `--max-context-length 1024`; today's
model-derived default is different. Match checkpoint, toolchain and compiler
settings, verify that the intended projections were replaced, and inspect
unaffected kernels when recompilation could explain a gain or regression.

Future work may investigate packed-projection memory efficiency, guarded
alignment specialization or the head. Recalibrate on the target: the GB10 gain
is not an L20 expectation, and neither result establishes behavior for 4B.
Hardware clocks, packaged arithmetic and native workload boundaries all need
to match the evidence used for a performance claim.
